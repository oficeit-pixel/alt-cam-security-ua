# Telegram webhook на бесплатном Render

Режим включается только непустой переменной окружения `TELEGRAM_WEBHOOK_URL`.
Значение для текущего сервиса:
`https://alt-cam-crm-api.onrender.com/telegram/webhook`.
Сначала развернуть и проверить код, затем добавить эту переменную в Render.
`ENABLE_BOT_POLLING=false` рекомендуется для ясности; webhook имеет приоритет
над polling, поэтому одновременно они не запускаются.

Секрет проверки заголовка Telegram вычисляется сервером как HMAC от существующего
`BOT_TOKEN` с отдельным контекстом. Не копировать токен в URL, клиентский код или
репозиторий. Нового секрета владельцу передавать не нужно. Запрос без верного
`X-Telegram-Bot-Api-Secret-Token` получает 401 до обработки обновления.

При запуске регистрируются те же обработчики и типы обновлений, включая кнопки
менеджеров и Business. Накопленные обновления не удаляются. HTTP-ответ ожидает
обработку, чтобы процесс не подтверждал сообщение до начала его обработки.
Как и любой webhook, доставка допускает повторные попытки Telegram; это не
гарантия exactly-once после сбоя процесса. Существующие проверки дублей заявок
должны сохраняться.

Проверка после переключения: `/health` — db:true; в журнале сообщение
`Telegram webhook active; polling disabled`; сообщение отдельного тестового
клиента получает ответ и карточку в группе менеджеров; второй клиент не видит
первую переписку; перехват менеджером выключает ответ ИИ для этой заявки.
Не считать 401 при открытии webhook без секрета неисправностью.

Откат: очистить `TELEGRAM_WEBHOOK_URL`, установить `ENABLE_BOT_POLLING=true`
и перезапустить сервис. Код удалит webhook без очистки ожидающих обновлений.
Webhook не устраняет холодный запуск Render, не делает фоновые SLA-задачи
непрерывными и не гарантирует мгновенный ответ: входящий запрос запускает сервер,
а при таймауте Telegram повторит доставку. Для постоянных фоновых задач нужен
постоянно работающий процесс либо отдельный планировщик с устойчивой очередью.
