# Alt-Cam Security UA

Односторінковий адаптивний лендинг українською мовою. Для запуску достатньо завантажити файли `index.html`, `styles.css` і `script.js` в одну папку на хостингу.

## Перед публікацією

Відкрийте початок `script.js` і замініть значення у блоці `CONTACTS`:

- `telegram` — ім’я користувача без `@`;
- `whatsapp` — номер лише цифрами, наприклад `380XXXXXXXXX`;
- `phone` та `phoneLabel` — номер і його підпис на сайті;
- `email`, `facebook`, `instagram`, `tiktok` — реальні контакти проєкту.

Поки Telegram і WhatsApp не вказані, кнопки відкривають стандартне меню поширення месенджера з уже сформованим текстом заявки.

Сайт не потребує backend: після заповнення форми заявка передається у вибраний месенджер. Для роботи шрифту Manrope потрібне інтернет-з’єднання; якщо Google Fonts недоступний, браузер використає системний шрифт без порушення верстки.

## Калькулятор

На сайті працюють три режими калькулятора:

- відеоспостереження — кількість внутрішніх, вуличних і PTZ IP-камер, NVR, WD Purple, точковий розрахунок витратних матеріалів та монтажу;
- резервне живлення — навантаження, напруга збірки, ємність і кількість АКБ, DOD та ККД інвертора з результатом у годинах і хвилинах;
- Ajax, СКУД і домофонія — Hub 2, датчики, замок Yli, контролер, IP-домофон Hikvision, автоматичне додавання ББЖ та кабельної продукції.

Результати є попередньою оцінкою, а не публічною офертою.

Орієнтовні ціни обладнання та робіт знаходяться у функції `calculateSecuritySystem()` у файлі `script.js`. Їх можна змінити відповідно до актуального прайсу без редагування верстки.

## Перед фінальною публікацією версії 2.0

- Замініть демонстраційні відгуки на перевірені відгуки реальних клієнтів.
- Додайте секцію власних робіт після того, як матимете 10–15 якісних фотографій виконаних об’єктів.
- Вкажіть реальні Telegram, Messenger, Viber, телефон та соціальні мережі у `CONTACTS`.
- Замініть `https://alt-cam.ua/` у `index.html`, `robots.txt` і `sitemap.xml`, якщо сайт буде розміщений на іншому домені.
- Оновіть телефон, email і посилання у JSON-LD блоці `LocalBusiness` в `index.html`.

Стокові фотографії не використовуються.

## CRM та аналітика

На початку `script.js` є блок `INTEGRATIONS`:

- `crmWebhook` — адреса Google Apps Script або CRM webhook для одночасної передачі заявок у Google Sheets, Telegram та Email;
- `ga4Id` — ідентифікатор Google Analytics 4;
- `metaPixelId` — ідентифікатор Meta Pixel;
- `clarityId` — ідентифікатор Microsoft Clarity.

Meta Conversion API потребує серверного або CRM-шлюзу і не може безпечно працювати лише у статичному браузерному коді.

Стартові ціни у каталозі необхідно звірити з актуальним прайсом перед запуском реклами.
# Перенос базы в Neon

## Настройки (владелец задаёт вручную, не в Git)

В Render → `alt-cam-crm-api` → Environment → `DATABASE_URL` вставьте
**прямой** PostgreSQL endpoint Neon, без `-pooler`, в формате:

```text
postgresql://USER:PASSWORD@ep-XXXX.eu-central-1.aws.neon.tech/altcam?ssl=require
```

Это пример с плейсхолдерами, а не реальные реквизиты. Используйте фактическое имя
базы из Neon (оно может быть `neondb`, а не `altcam`). Спецсимволы пароля должны быть
URL-encoded. Стандартный Neon URL с `sslmode=require&channel_binding=require` тоже
поддерживается: код удаляет несовместимые параметры и передаёт asyncpg `ssl=require`.
URL и пароли не отправляйте в чат, не сохраняйте в репозиторий или команды истории.

`AUTO_CREATE_DB=true` — основной существующий способ создания схемы:
`Base.metadata.create_all` + `migrate_web_orders` + `migrate_admin_auth`.
Все модели теперь явно импортируются перед созданием таблиц. Повторный запуск
идемпотентен. Альтернатива для **пустой** базы — `python -m alembic upgrade head`;
ревизия `20260927_0004` дополняет старую историю до схемы CRM и токенов авторизации.
Не запускайте начальные Alembic-миграции поверх базы, уже созданной `create_all`,
без отдельной сверки и корректного baseline/stamp.

В CRM задайте `ENABLE_BOT_POLLING=true`, во втором `alt-cam-manager-bot` — `false`
(либо остановите второй сервис вручную). Бот для исходящих уведомлений может
оставаться настроенным в обоих, но получать Telegram updates должен только один.
`DATABASE_URL` обоих сервисов задаётся через Dashboard (`sync: false`).
Blueprint и переменные сами по себе в этом изменении **не применяются**.

## Ручной перенос старых данных

Старая база Render сейчас приостановлена. Для `pg_dump` её нужно временно
восстановить либо использовать ранее созданный бэкап. Если источника/бэкапа нет,
**пропустите скрипт переноса**: backend создаст пустую схему в Neon. Старые заказы,
пользователи и цены при этом не восстановятся автоматически.

1. Установите Python 3 и клиентские утилиты PostgreSQL 17 (`pg_dump`, `pg_restore`,
   `psql`) в PATH. Остановите запись в обе базы на время переноса и проверки.
2. Сделайте отдельный бэкап целевой базы. В приватном окружении процесса задайте
   `OLD_DATABASE_URL` и `NEW_DATABASE_URL`; используйте прямые endpoints.
3. Скрипт **заменяет таблицы в целевой базе** (`--clean --if-exists`). Только после
   проверки назначения задайте `CONFIRM_NEON_RESTORE=YES`.
4. Linux/macOS: `bash scripts/migrate_render_to_neon.sh`.
   Windows: `powershell -File scripts/migrate_render_to_neon.ps1`.
   Значения URL не передаются аргументами и не печатаются; libpq получает их из
   окружения. Временный дамп содержит персональные данные: используйте доверенный
   компьютер и защищённую временную папку. Скрипт удаляет дамп при завершении.
5. Если старая база недоступна, скрипт остановится **до восстановления в Neon**.
   Если переменные не заданы, он сообщает `SKIPPED`. Не считать это переносом.
6. Restore выполняется одной транзакцией. Затем синхронизируются serial/identity
   sequences по максимальным значениям столбцов, выводится сравнение числа строк
   всех пользовательских таблиц. При несовпадении код возврата — 1: запись не
   возобновлять до выяснения причины. Удалите переменные миграции из окружения.
7. Готовый custom-format бэкап можно восстановить `pg_restore` вручную с теми же
   флагами; без доступного источника сравнение двух баз невозможно — проверяйте
   количество строк по сохранённому отчёту бэкапа.

## Проверки после отдельного одобрения деплоя

- `/health` возвращает HTTP 200 и `{"ok":true,"db":true}`. `db:false` означает
  только доступный HTTP-сервер, **не** готовность принимать/сохранять заказы.
- При отказе БД: пять ограниченных по времени попыток инициализации; затем HTTP
  продолжает работать, `/health` проверяет БД с таймаутом 5 секунд. Первый probe
  после сна Neon может вернуть false — повторите после пробуждения.
- Проверьте вход в CRM, данные заказов, цены и одного polling-бота; не создавать
  реальные заказы поставщикам для тестирования. Накопленные updates не удаляются.
- После восстановления соединения с **новой пустой БД**, если начальная
  инициализация исчерпала попытки, перезапустите сервис для создания схемы.
- Логи не должны содержать connection URL. После сна соединения проверяются
  `pool_pre_ping`, перерабатываются через 300 секунд; пул 5 + до 5 дополнительных.

## Локальные тесты

```text
python -m pip install -r bot/requirements-dev.txt
python -m pytest tests/backend -q
```

Интеграционные тесты PostgreSQL пропускаются без `TEST_POSTGRES_URL`. Для полного
прогона запустите одноразовый локальный `postgres:17`, задайте `TEST_POSTGRES_URL`
на его базу `postgres` и повторите pytest. Тест создаёт и удаляет только собственные
базы `altcam_test_<uuid>` на localhost; проверяет отдельно runtime и Alembic, таблицы,
столбцы и `db:true`. Workflow `neon-db-tests.yml` содержит PostgreSQL 17 service и
не выполняет деплой. Ручной workflow в рамках этой работы не запускался.
